1. Kiến trúc hệ thống

Hệ thống gồm một backend monolith Spring Boot dùng chung cho nhiều công ty (multi-tenant chung schema, phân tách bằng cột company_id), một app Flutter chạy được cả web lẫn Android, và các dịch vụ ngoài: AWS S3, Firebase FCM, OpenStreetMap.

Hình 1. Thành phần chính. Backend không tách worker riêng: scheduler chạy chung tiến trình với API.

Đường đi của một request

  1. Client gửi request kèm Authorization: Bearer <JWT>, Accept-Language, X-Device-ID.
  2. Spring Security chọn chain: /admin/** (yêu cầu ROLE_SYSTEM_ADMIN) hoặc /api/v1/** (chỉ yêu cầu đã đăng nhập).
  3. JwtAuthFilter đọc token, nạp user từ DB (trừ token impersonate), đặt vào SecurityContext. Lỗi token bị nuốt im lặng → request đi tiếp như ẩn danh.
  4. Controller tự kiểm quyền bằng requirePermission(...) hoặc user.can(...) (lặp ở 15 controller, không có chốt chặn tập trung).
  5. Service/Repository lọc theo companyId lấy từ user và theo tập phòng ban được phép (DeptScopeService).
  6. Lỗi nghiệp vụ ném ResponseStatusException → ApiExceptionHandler dịch key error.* theo ngôn ngữ.

Hình 2. Luồng đăng nhập, gọi API và refresh. Rủi ro liên quan: mục S1–S6 ở trang Đánh giá.

3 loại token
  • COMPANY: user công ty, 24h, mang companyId + permissions.
  • REFRESH: 7 ngày, lưu jti trong user_sessions, xoay vòng mỗi lần dùng.
  • SYSTEM: system admin, 24h, không có refresh.
  • Impersonate: token COMPANY có cờ impersonated, toàn quyền, 24h.
Mô hình quyền
  • Quyền = role ∪ quyền trực tiếp (quyền trực tiếp ghi đè theo module).
  • ~33 mã quyền theo module (EMPLOYEE_*, ATTENDANCE_*, LEAVE_*, PAYROLL_*...).
  • VIEW là tiền đề của quyền khác trong module.
  • Quyền được nạp lại từ DB mỗi request → đổi role có hiệu lực ngay.
Phạm vi phòng ban
  • Gắn theo từng quyền (role hoặc user).
  • Mã đặc biệt: −1 chỉ mình tôi, −2 phòng tôi, −3 phòng tôi + cấp con.
  • Mở rộng con cháu bằng BFS.
  • Tập rỗng = toàn công ty (fail-open — xem R5).

Nhận xét kiến trúc

Hợp lý ở giai đoạn hiện tại
  • Monolith + MySQL đủ đơn giản cho quy mô vài chục công ty, dễ deploy trên EB.
  • Engine tính công (AttendanceCalculator) và tính lương (FormulaEngine) tách riêng, không phụ thuộc DB, dễ viết test.
  • Universal Excel dùng mô hình descriptor: thêm module mới chỉ cần một bean.
  • Tách hai security chain cho system admin và user công ty.
Cần chỉnh
  • AttendanceController 1.771 dòng chứa logic nghiệp vụ và @Transactional; 9 chỗ transaction ở controller.
  • Kiểm quyền thủ công lặp 15 lần → dễ quên (đã quên ở approve chấm công, dashboard, báo cáo).
  • Scheduler chạy trong API, dùng múi giờ JVM, không khoá phân tán → lệch giờ và gửi trùng khi scale.
  • Không có health check, metrics, audit log; lỗi token bị nuốt không log.
  • FE: 12 file trên 1.000 dòng, logic gọi API nằm trong widget, không có test.
